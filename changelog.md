# Changelog

## 2026-10-24 — оптимизация Triton kernels для H200

Исходная версия проекта была разработана под Tesla V100 без нативных bf16 tensor cores. В этой итерации добавлен нативный bf16 для современных GPU, оптимизированы decode kernels и повторены измерения на NVIDIA H200.

Для оценки именно изменений кода исходные kernels из коммита `e1fda78` и обновлённые kernels запускались **на одном физическом H200, GPU 4**. Полные модели оценивались отдельно на GPU 5. Окружение: torch 2.5.1+cu121, Triton 3.1.0, transformers 4.49.0; зависимости не менялись. Подробности оборудования: [hardware.json](results/h200/hardware.json).

### Что изменено

| Область | До | После |
|---|---|---|
| bf16 в GEMM | Все bf16 operands передавались как `int16` bits и преобразовывались в fp16 для tensor cores V100 | На Ampere и новее используется нативный bf16; старый путь преобразования оставлен для Volta |
| Диапазон bf16 activations | При преобразовании в fp16 значения ограничивались диапазоном ±65504 | Нативный bf16 сохраняет свой диапазон; добавлены проверки activations со значением 131072 |
| Деквантизация W4 | `(q - zero) * scale` вычислялось с промежуточным округлением в fp16 | Вычисление в fp32 с одним округлением в dtype activations; torch reference приведён к той же формуле |
| Decode, `M = 1` | Zero-fill → split-K GEMM с атомиками → преобразование результата: три GPU kernels | На Ampere и новее отдельный GEMV: один kernel, без scratch buffer и атомиков |
| Небольшие batches, `2 ≤ M ≤ 64` | Атомарное суммирование partial results в предварительно обнулённый fp32 buffer | Запись независимых split-K partial results и отдельная детерминированная редукция: два kernels |
| Autotuning prefill | Pipeline из двух стадий и исходный набор tiles | Добавлены tiles с `BLOCK_K = 128` для больших блоков и выбор между 2–4 стадиями |
| Autotuning decode | Split-K до 8; не было подходящих small-M tiles с `BLOCK_K = 32` | Split-K до 16; добавлены tiles для групп размера 32 |
| Ключи autotuning и dispatch | Autotuning не учитывал `GROUP_SIZE`; dispatch не различал новый и legacy bf16 paths | Добавлены `GROUP_SIZE` и признак legacy bf16; сохранён прямой запуск закешированных compiled kernels |
| Измерение конфигураций | Обычный autotuning | CUDA-graph autotuning; перед первым tuning добавлена синхронизация, необходимая из-за независимых streams в Triton 3.1 |

Формат packed weights, group-wise asymmetric quantization и размер группы по умолчанию `G = 128` сохранены. GPTQ/AWQ и калибровка не добавлялись. Совместимость legacy path с V100 в этой итерации повторно не проверялась.

### Kernels: до и после на одном H200

Время в миллисекундах — сумма семи linear layers одного decoder block Llama-3.2-1B: q/o 2048×2048, k/v 512×2048, gate/up 8192×2048 и down 2048×8192. Activations — bf16. Измерения используют CUDA-graph replay после прогрева, без compilation и Python dispatch. Ускорение рассчитано как `время до / время после` по исходным значениям JSON, до округления.

| Tokens M | W4 до, мс | W4 после, мс | Ускорение W4 | W16 до, мс | W16 после, мс | Ускорение W16 |
|---|---|---|---|---|---|---|
| 128 | 0.247 | 0.166 | **1.49×** | 0.217 | 0.087 | 2.50× |
| 512 | 0.389 | 0.316 | **1.23×** | 0.400 | 0.142 | 2.81× |
| 2048 | 1.186 | 1.064 | **1.12×** | 0.940 | 0.412 | 2.28× |
| 1, decode | 0.099 | 0.045 | **2.21×** | 0.110 | 0.029 | 3.74× |
| 16, decode | 0.114 | 0.068 | **1.68×** | 0.125 | 0.074 | 1.68× |

Для W4 наибольший выигрыш получен при `M = 1`: вместо трёх запусков выполняется один GEMV. Ускорения в таблице относятся ко всему набору изменений; отдельный вклад каждой оптимизации не измерялся.

Это microbenchmark с повторным использованием весов и L2 cache. Его ускорение нельзя напрямую переносить на полную модель. Исходный замер `M = 16` был повторён без пересечения с тестами; в итоговом JSON используются исправленные значения.

Источники: [исходные kernels на H200](results/h200/gemm_before.json), [обновлённые kernels на H200](results/h200/gemm.json), [лог итогового benchmark](results/h200/logs/bench_gemm.log).

### Полная модель на H200: результат после изменений

Следующая таблица сравнивает **текущий bf16 baseline и текущую INT4-модель**, а не старую и новую версии INT4 kernels. Полная модель с исходными kernels на H200 до изменений не измерялась.

WikiText-2 test: 141 неперекрывающееся окно по 2048 tokens. Prefill — один forward по 2048 tokens в CUDA graph. Decode — prompt 128 tokens и 128 decode steps со static KV cache и CUDA graph. В W4 g128 `lm_head` остаётся bf16.

| Метрика | bf16 / cuBLAS | Triton W4 g128 | Сравнение |
|---|---|---|---|
| Perplexity, меньше — лучше | 13.165 | 16.431 | Качество ухудшается из-за RTN-квантования |
| Prefill, мс / 2048 tokens | 14.03 | 26.01 | INT4 медленнее примерно в 1.85× |
| Decode, tokens/s | 379.4 | 415.7 | INT4 быстрее примерно на 10% |
| Веса decoder linears, MiB | 1856 | 493 | Меньше в 3.76× |
| Вся модель, MiB | 2357 | 994 | Меньше в 2.37× |
| Peak allocated memory при PPL evaluation, GiB | 4.84 | 3.48 | Снижение примерно на 28% |

Triton W4 и те же INT4-веса, деквантизированные и вычисленные через torch bf16, дали одинаковую PPL **16.431213687921**. Для Triton W16 и bf16 baseline PPL также совпала: **13.164691111385928**. Это подтверждает корректность вычислительного пути на данном наборе оценки; потеря качества INT4 относительно bf16 остаётся следствием квантования.

Дополнительно проверены группы 64 и 32: PPL **15.419** и **14.806** соответственно, при увеличении объёма метаданных. Вариант с квантованным `lm_head` даёт PPL **16.815**. Он занимает 1127 MiB вместо 994 MiB у обычного W4: разрыв связи с bf16 embeddings требует отдельной packed-копии выходной проекции.

Источники: [bf16 baseline](results/h200/llama_bf16.json), [W4 g128](results/h200/llama_w4.json), [деквантизированный reference](results/h200/llama_w4-fake.json). Все восемь вариантов приведены в [README](README.md).

### Исторические результаты: V100 → H200

Здесь показаны прежний отчёт и текущие результаты для **W4 g128**. Изменились GPU и методика части замеров, поэтому эти числа описывают переход проекта на новую машину и не являются оценкой ускорения только от оптимизации кода.

| Метрика W4 g128 | Раньше: V100 | Сейчас: H200 |
|---|---|---|
| Perplexity | 16.435 | 16.431 |
| Prefill, eager wall time, мс / 2048 tokens | 383.71 | 27.29 |
| Decode, CUDA graph, tokens/s | 125.2 | 415.7 |
| Веса decoder linears, MiB | 493 | 493 |
| Вся модель, MiB | 994 | 994 |

В строке prefill использован сохранённый eager wall time обоих запусков, а не новый graph-prefill показатель 26.01 мс. На V100 host был сильно загружен; новый decode graph также включает копирование tokens и обновление позиции cache. Числа не полностью сопоставимы даже помимо различия GPU. Снижение памяти 2357 → 994 MiB обеспечивалось INT4-форматом уже в исходном проекте и не является результатом этой оптимизации.

Архив: [прежний README](results/v100/README.md), [прежние результаты W4](results/llama_w4.json). Исходные V100 JSON и logs сохранены на прежних местах.

### Изменения benchmark и проверок

- В `benchmarks/bench_gemm.py` добавлены `--tokens`, создание выходной директории и metadata: GPU, compute capability, версии torch/Triton/CUDA, group size и время запуска.
- В `benchmarks/eval_llama.py` добавлен graph-prefill benchmark; прежний eager wall time сохранён отдельно. Копирование следующего token и увеличение cache position перенесены внутрь decode graph; после warmup и capture восстанавливается исходный prompt/cache. Добавлены GPU-event timings, checkpoint revision и параметры запуска.
- Число correctness tests выросло с **74 до 85**. Добавлены группы 32/64, граница между small-M и prefill, strided inputs, повторные cached launches, детерминированность split-K и значения bf16 за пределами диапазона fp16. Итог: **85 passed** на H200, [лог](results/h200/logs/pytest.log).
- [README](README.md) обновлён замерами H200 и ограничениями сравнения с cuBLAS. Новые JSON и logs размещены в [results/h200](results/h200).
- Для окружения установлен `uv`/`uvx` в `~/.local/bin`, который уже входит в пользовательский `PATH`; зависимости установлены через `uv sync --frozen`.

Основные изменённые файлы: [gemm.py](int4_triton/gemm.py), [quantize.py](int4_triton/quantize.py), [bench_gemm.py](benchmarks/bench_gemm.py), [eval_llama.py](benchmarks/eval_llama.py), [test_kernels.py](tests/test_kernels.py).
